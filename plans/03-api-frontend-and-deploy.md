# Plan 3: API, frontend and deployment

**Goal:** a web app where anyone uploads files or a URL, chats with them and sees sources. No accounts.

**Depends on:** Plans 1 and 2 (the ingestion and query functions).

## Sessions without auth

The browser holds a random session id (generated by the server on first upload, kept in `localStorage`). Every request sends it. The id is the only access control, so it must be unguessable (it is a UUID4) and sent in a header, never put in logs or shared URLs. Tell users the limit: anyone who has the session id can see that session's documents.

## FastAPI endpoints

| Endpoint | Purpose |
|---|---|
| `POST /sessions` | create a session, return the id |
| `POST /sessions/{id}/files` | upload one or more files (multipart); return a per-file status |
| `POST /sessions/{id}/urls` | add a URL to scrape and index |
| `GET /sessions/{id}/documents` | list documents and their indexing status |
| `DELETE /sessions/{id}/documents/{doc_id}` | remove one document |
| `POST /sessions/{id}/chat` | ask a question, return `answer` + `sources` (stream later) |
| `DELETE /sessions/{id}` | delete everything for the session |

Rules:
- Validate the session id with `validate_session_id`; reject bad ids with 400.
- Indexing runs as a background task (large files take time). Status per document: `queued`, `processing`, `ready`, `failed` with a reason. The chat endpoint says which documents are not ready yet.
- Enforce file size, file count and allow-listed extensions at the API edge, not just in the loaders.
- Rate limit per IP (uploads and chat), since there is no account to throttle.
- CORS limited to the frontend origin; request-size limit; no stack traces in responses.

## Next.js frontend

1. Upload area: drag and drop, many files, a URL box, per-file status chips.
2. Chat panel: messages, streaming answer, "not found in your documents" state.
3. Sources: each answer shows numbered source cards (file or URL, page or rows, quoted passage); clicking a citation `[1]` highlights its card.
4. Document list with delete, and a "clear session" button.
5. Clear errors for rejected or failed files. Mobile-friendly layout.

## Deployment

- Backend container (Python 3.13, `uv sync --frozen`, Playwright browsers if the scraper runs there). Disk can be ephemeral because raw files are only needed during indexing.
- Frontend on a static/Node host. Environment variables set in the host, never in the repo.
- Scheduled job: delete session folders and Pinecone namespaces after N days of inactivity.
- Logging without document contents or session ids; basic metrics (upload failures, answer latency, "not found" rate).

## Done when

- A new visitor uploads a PDF and a URL, asks questions and sees correct sources, with nothing to sign up for.
- Two browsers cannot see each other's documents.
- The deployed app survives a restart (sessions are still answerable from Pinecone) and cleanup removes stale data.
- An end-to-end test (upload, wait for `ready`, ask, check sources) passes in CI.

## Risks

- Anonymous upload endpoints invite abuse (large files, scraping internal URLs): block private IP ranges in the URL scraper (SSRF), cap sizes and rate limit.
- Cost is uncapped without accounts: set daily limits on vision calls, embeddings and Groq requests.
